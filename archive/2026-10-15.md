## 2. Better HTTP/1 connection reuse in Go 1.27

원문: <https://go.dev/blog/http-connection-reuse> (Hacker News)

🌐 Everyone
Go 1.27에서는 같은 서버에 여러 번 요청할 때 매번 새로운 네트워크 연결을 만들던 것이 개선되어, 전체 실행 속도가 크게 빨라졌습니다. 이전 버전에서는 응답 본문을 읽지 않으면 연결을 재사용하지 못해 매번 연결 설정 비용이 발생했습니다.

💻 Developers
읽지 않은 응답 본문 차단은 net/http가 응답 본문을 완전히 소비하지 않으면 해당 TCP 연결을 폐기하도록 설계된 동작을 말합니다. Go 1.27에서는 이 동작을 자동으로 본문을 소모하거나 재사용 가능하도록 수정했지만, 여전히 전체 응답을 버리는 비용이 발생할 수 있습니다.

🔬 Researchers
읽지 않은 응답 본문 차단은 HTTP/1.1에서 연결 재사용을 방해하는 주요 원인으로 남아 있지만, TLS 1.3 환경에서의 핸드셰이크 최적화와 같은 다른 레이어의 비용이 전체 지연에 미치는 비중은 아직 정확히 규명되지 않았습니다. 향후 연구에서는 다양한 서버 구현과 스트림 종료 패턴을 포함한 실험을 통해 재사용 효율을 정량화하고, API 수준에서 안전한 재사용을 보장하는 설계 방안을 모색해야 합니다.

## 3. Jeva: System One Models from First Principles

원문: <https://arxiv.org/abs/2610.18773> (Hugging Face Papers)

🌐 Everyone  
AI가 질문에 대해 여러 선택지 중 하나를 고를 때 기존 시스템은 답이 없을 때와 후보가 많을 때 속도가 떨어지는 문제를 가지고 있었습니다. Jeva는 이러한 문제를 해결해 답이 없음을 바로 알리고, 선택지 순서와 개수에 관계없이 빠르게 결정하도록 만들어 일상 서비스에서 더 신뢰할 수 있는 결과를 제공합니다.  

💻 Developers  
Jeva architecture는 request와 각 option을 별도의 shared encoder로 변환하고, 불변 option memory와 request 상태를 결합하는 경량 decision stack을 통해 permutation invariance와 option scalability를 구현합니다. 이 설계는 option representation을 재사용해 cross‑request cache를 가능하게 하여 latency를 크게 낮추지만, option memory를 유지하고 별도 coverage estimate 모듈을 실행하기 위한 추가 memory와 compute가 요구됩니다.  

🔬 Researchers  
Jeva가 null detection과 permutation‑equivariant 확률을 거의 완벽하게 구현한다는 평가에도 불구하고, 다양한 도메인에서 coverage estimate의 일반화 한계와 학습 시 후보 집합 변화에 대한 민감도가 아직 완전히 규명되지 않았습니다. 이러한 미해결 과제는 대규모 동적 후보 풀에서의 효율적인 메모리 관리와 옵션 표현 재사용이 모델 편향에 미치는 영향을 정량화하는 새로운 벤치마크와 ablation 연구가 필요합니다.
